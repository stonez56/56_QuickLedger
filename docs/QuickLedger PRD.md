# QuickLedger 產品需求文件（PRD）

## 1. 文件資訊

- 產品：56 QuickLedger
- 功能：統編查詢與發票抬頭輔助填寫
- 版本：PRD v1.0
- 狀態：待確認
- 日期：2026-11-04
- 相關分支：`codex/invoice-input-ubn`

## 2. 背景與問題

目前「新增憑證」的「憑證資訊」卡片已有統一編號欄位，能做 8 碼與檢查碼驗證，但使用者仍需自行查找並輸入對方名稱。現有資料模型只保留統一編號，沒有專用的發票抬頭欄位，因此：

1. 使用者無法在輸入當下快速確認統編是否對應正確對象。
2. OCR 或人工輸入後，沒有可靠的名稱建議可以核對。
3. 查詢失敗時若直接阻擋送出，會讓結帳或記帳流程被外部服務拖慢。

本功能使用 `paid-tw/tw-ubn` 提供的查詢服務，以統一編號查詢登記名稱，作為「可接受、可修改、不可阻塞」的輔助資訊。

## 3. 目標

### 3.1 使用者目標

- 輸入完整且格式正確的 8 碼統編後，可以看到登記名稱建議。
- 使用者可以一鍵採用建議，也可以自行修改名稱。
- 查無資料、服務逾時或服務不可用時，仍可手動輸入並正常送出憑證。
- 進項與銷項都沿用同一套互動；欄位標籤依目前的「供應商／買受人」語意顯示。

### 3.2 產品目標

- 降低統編與對方名稱不一致的輸入錯誤。
- 保持現有記帳流程與 Google Sheet 相容，不破壞歷史資料。
- 不把外部查詢當成稅務判定或送出必要條件。

## 4. 非目標

- 不取代使用者對紙本或電子發票的核對。
- 不因公開資料查無而判定統編無效。
- 不自動修改發票金額、稅額、課稅別、會計科目或帳別。
- 不儲存統編查詢的完整上游回應、IP、追蹤識別碼或不必要的個人資料。
- 不在本階段加入名稱搜尋、批次匯入或公司資料庫管理頁。

## 5. 現況 UI/UX 審查

### 5.1 現有流程

1. 使用者進入「新增憑證」。
2. 在「憑證資訊」卡片選擇進銷別、日期與格式代號。
3. 發票號碼與統編並列於同一列。
4. 統編欄位在輸入後顯示格式錯誤或綠色成功圖示。
5. 使用者按下「確認送出」，通過表單檢查後再確認。

### 5.2 審查結果

- 統編已經是使用者輸入對方資料的自然位置，功能應直接附著在該欄位。
- 不適合新增獨立「公司資料」卡片：會增加垂直高度與欄位跳轉，且查詢只依賴統編。
- 綠色圖示目前只表達「檢查碼正確」，不能誤導成「公司已查到」；查詢結果應使用獨立文字狀態。
- 查詢狀態應出現在統編欄位下方，讓錯誤與建議靠近輸入來源；不可只放在頁尾訊息區。
- 現有固定底部操作列應保留；查詢中的按鈕不應鎖住整張表單或送出按鈕。

## 6. 目標流程與介面方案

### 6.1 建議放置位置

在「憑證資訊」卡片的統編欄位內，於統編輸入框正下方加入一個內嵌查詢區：

```text
對方統一編號 *                 ✓ 格式正確
[ 12345678                         ]
登記抬頭（選填）
[ 台灣範例股份有限公司                 ]
✓ 已找到登記名稱                 [套用]
```

`登記抬頭` 是可編輯欄位；查詢回傳的名稱只是建議值。若使用者已自行填寫名稱，查詢完成後不得靜默覆寫。

### 6.2 觸發時機

- 統編長度達 8 碼且本地檢查碼正確時，在 `blur` 觸發查詢。
- 若使用者停留在欄位內持續輸入，不逐字呼叫服務。
- 統編變更時取消上一個未完成請求；回應只可更新目前統編對應的畫面。
- `99 - 收據／其他` 不強制查詢；使用者仍可手動輸入統編與抬頭。

### 6.3 查詢狀態

| 狀態 | 畫面文案方向 | 使用者可做的事 |
|---|---|---|
| 尚未查詢 | 輸入 8 碼統編後自動查詢 | 繼續填寫 |
| 查詢中 | 正在查詢登記名稱… | 繼續填寫其他欄位；不可重複送出同一查詢 |
| 找到 | 已找到登記名稱：`{name}` | 按「套用」或自行編輯 |
| 已停業／已註銷 | 顯示名稱與狀態提醒 | 仍可套用；不阻擋送出 |
| 查無公開資料 | 查無公開資料，仍可手動填寫 | 自行輸入；不顯示「統編錯誤」 |
| 上游不可用 | 查詢暫時無法完成，請手動填寫 | 重新查詢或繼續送出 |
| 名稱不可安全使用 | 名稱無法自動帶入，請手動確認 | 手動輸入；不直接呈現私用區造字 |

### 6.4 互動與無障礙

- 統編、抬頭欄位都有可見標籤，不以 placeholder 取代標籤。
- 查詢狀態使用 `role="status"`，錯誤使用與欄位關聯的 `aria-describedby`。
- 「套用」是有文字的按鈕，不使用只有圖示的控制項；手機觸控區至少 44px。
- 查詢服務錯誤不得只顯示頁尾 toast；狀態必須靠近統編欄位。
- 送出驗證失敗時，保留現有欄位錯誤，並讓鍵盤使用者可找到第一個錯誤。
- 深色模式維持現有焦點環與語意色彩；查詢成功不可只依靠綠色表達。

## 7. 功能需求

### FR-01 本地統編驗證

- 沿用既有 `isValidTaiwanTaxId`。
- 非 8 碼或檢查碼錯誤時，不呼叫 UBN 服務。
- 格式代號為 `99` 時，不因缺少統編或查詢失敗阻擋送出。

### FR-02 統編查詢

- 查詢端點由 `VITE_UBN_BASE_URL` 設定，不在原始碼硬編碼服務網址。
- 使用 `/v1/vat/{ban}` 查詢。
- 預設逾時 1500ms；逾時、網路錯誤、非預期回應都回到可手動輸入狀態。
- 查詢只接受 allow-list 欄位：`found`、`ban`、`name`、`status`、`source`、`nameHasPrivateUse`。

### FR-03 名稱套用與編輯

- 回傳 `found: true` 且名稱可安全使用時顯示建議。
- 使用者按「套用」後，將名稱寫入 `counterpartyName`。
- 使用者可在抬頭欄位修改；儲存時以使用者最後確認的內容為準。
- 不自動把名稱塞入備註欄位，避免名稱與業務說明混在一起。

### FR-04 送出與歷史資料

- `counterpartyName` 隨 `submit`／`update` 寫入總帳。
- 舊資料沒有抬頭欄位時顯示空白，不影響歷史查詢、編輯、刪除與報表。
- 查詢服務不可用時仍可完成憑證送出。

## 8. 驗收條件

1. 輸入正確 8 碼統編並離開欄位後，畫面在逾時內顯示查詢中，再顯示名稱建議。
2. 按「套用」後，抬頭欄位可見名稱且可修改。
3. 將統編改成另一組，舊查詢結果不會覆蓋新統編的名稱。
4. 查無公開資料時，畫面不顯示「統編錯誤」，且仍可手動輸入與送出。
5. 服務逾時或回傳 502 時，表單仍可送出，且不產生未確認的抬頭資料。
6. `99` 格式代號可不查詢、不輸入抬頭而完成既有流程。
7. 新增與編輯流程都能保留 `counterpartyName`；舊資料仍可正常編輯。
8. 桌面與手機寬度下，統編狀態、抬頭欄位與「套用」按鈕不溢出、不被固定底部操作列遮住。
9. 使用鍵盤 Tab、Enter、Escape 可完成輸入、套用與送出；狀態文字可被螢幕閱讀器讀取。

## 9. 驗證計畫

- 規格：確認本 PRD 與 DB PRD 的欄位、狀態與 API 回應一致。
- 本地：TypeScript、建置、既有資安測試；補上 UBN 查詢狀態與競速回應測試。
- UI：桌面與手機 viewport，驗證統編輸入、查詢中、找到、查無、逾時與手動覆寫。
- 整合：使用合成統編與測試 UBN endpoint，不傳送真實個人資料。
- 發布：先推送分支並建立 PR；通過審查後才進入 Staging，未經明確核准不部署 Live。

## 10. 風險與決策

- 公開資料不一定涵蓋所有合法統編；因此「查無」永遠不是驗證失敗。
- 外部服務延遲會影響感受；查詢必須是非阻塞、可逾時且可手動完成。
- 登記名稱可能包含不可直接呈現的私用區造字；遇到此狀況只提示手動輸入，不把原字串直接帶入。
- 本階段不保存查詢來源與狀態，避免把暫時性外部資訊變成帳務事實；未來若有稽核需求再另行設計欄位。
